# Phase 02.1 Plan 03: Hypothesis screens, X8 and X9s sham sync Summary

**Consumer-side `waitsync()` before `EncodeFrameAsync` (X5) cures the concurrent-encode corruption at ~0 % fps cost (0/20, md5 60/60 S), but a 4 ms CPU-only sham delay cures it as well, so the fix is labelled a timing-workaround; the ordering defect below the API is flagged for Phase 3/upstream.**

## X8 masking

LIBVA_TRACE (BUFDATA off) gave 0/20 with fps -26 % (166.9/109.9/170.1). Per A9 the absence is attributed to the tracing, so no corrupt run was captured and the planned VA ordering analysis (classes a/b/c) was not performed.

## X9s result

- diag-T3 (`diag/surf-trace` commit `3b12a786`, sha256 `1b95023e6a0ffa3be93a0c2df14c0b034398e98e0d7b337cd033b0f45f4d704b`) toggles-off bit-exact 6/6.
- Real waitsync distribution (3-way harness, 2 iterations): median 6.8-11.1 us, mean 344-841 us, p90 1.2-2.6 ms, p95 2.1-4.0 ms, p99 5.1-8.2 ms, max 6.9-13.6 ms. Sham = 4000 us (max hot-scene p95).
- Sham screen: 20 valid iterations, 0 corrupt, md5 60/60 S, fps 146.8/112.3/143.7 (stock 226.6/131.2/230.1).
- Pre-registered logic: sham 0/20 + md5 all S => a CPU delay of the same size cures it => mechanism B (timing window); X5 stays a valid ffmpeg-equivalent workaround, the root ordering defect lies below the API (driver/kernel cross-context fencing) -> flag for Phase 3/upstream.
- Caveats: the sham is 4 ms on every frame vs a real median wait of ~7 us, i.e. a large perturbation of the X3/X8 class (not a minimal timing change); a smaller sham was not run; the "below the API" reading is consistent with B but not directly observed.

## Drift-mode observations

Mid-stream md5-D with a harness-clean verdict (different from the tail 295..299 mode) was seen once in T2-pc (it03 1129) and once in X3 (it14 1129); it was absent in all 60 cells of each of X5, X6, X8 and X9s. `d01_md5.sh` is mandatory on every candidate because `cand_screen.sh` is fail-open for this mode.
