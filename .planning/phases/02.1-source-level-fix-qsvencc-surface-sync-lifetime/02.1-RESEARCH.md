## Summary

**The mechanism question is already answered by the offline pass (D-01), and it reshapes the phase.** All 30 saved corrupt frames (13 from the 8.31 batch, 17 from the Phase-1/8.22 batch) are **stale content from the SAME session**, not cross-session content: output frame 299 re-encodes an *earlier source frame of its own chunk* — source frame 289, 291 or 294 for scene 923, source frame 290 for scene 1129 — at 47–57 dB against the isolated reference (unrelated frames score 10–20 dB), and 40–41 dB against the software-decoded SOURCE. The corrupt frame is always the **hidden ARF anchor of the final, truncated 5-frame mini-GOP [295..299] that is forced by the IDR at display 300** (`--gop-len 300`); frames 295–298 then show small reference drift (52–56 dB) and nothing else in the 340/362-frame chunk ever differs (verified on all 30 outputs). So the input surface of one specific `EncodeFrameAsync` call (chunk frame index 299) contains an older frame of the same stream when the GPU encoder reads it. "Concurrency" only perturbs timing. This is a stale-input-surface race inside one process (hypotheses 1/2), not an allocator-identity or cross-session problem.

**The static comparison singles out one edge.** qsvencc 8.31 has exactly one `SyncOperation` call site in the whole pipeline (`qsv_pipeline_ctrl.h:352`, only reached for the encoder's bitstream), so DEC→VPP and VPP→ENC are handed over with no CPU sync. ffmpeg n6.1.1 does the same for DEC→VPP (it even skips the decoder sync for QSV frames, `qsvdec.c:790-794`), but **syncs every VPP output before the encoder sees it** (`qsvvpp.c:1024-1036`, `vpp_qsv` default `async_depth=0`, `vf_vpp_qsv.c:882`), uses a 64-surface VPP-out pool and a LIFO pool, and hands the encoder a *copy* of the surface struct. Session topology (separate sessions, joined) is the same; qsvencc has two per-edge pools, not one OR-combined pool. Reading vpl-gpu-rt 26.2.2 shows the scheduler already orders ENC after VPP by `mfxFrameSurface1*` identity and chains AV1 encode tasks (`MFX_TASK_THREADING_INTRA`), the encoder holds the input surface `Locked` until its task is freed, there is no Raw copy for video-memory input, and the Linux media-driver's `Mos_Specific_SyncOnResource` is an empty stub (ordering rests on kernel implicit fencing) — so a pure "missing wait" is NOT the obvious explanation; the sync experiment may cure it by timing/serialisation rather than by adding a missing edge. Two further facts from the parameter audit: qsvencc never assigns the encoder's `mfxVideoParam.AsyncDepth` (the AV1 runtime default is 5 ⇒ up to 2 parallel GPU submits), and the CLI `--async-depth` only changes pool sizes and the VPP — so the earlier "`--async-depth 1` is inert" result says nothing about encoder-side parallelism. That is exactly why the plan must measure, not assume.

**Primary recommendation:** Build ONE diagnostic binary on a branch off tag `8.31` (separate commit: env-gated in-memory surface trace + env-gated coarse toggles: consumer-side `waitsync` before `EncodeFrameAsync`, `waitsync` after decode, pool +16 / round-robin reuse, optional encoder AsyncDepth), gate it with one N=20 official batch (≥7 of 40 hot-scene exposures must still corrupt), then walk the experiment ladder with sequential early-stop screening through the unmodified harness via a PATH shim. Run the VPP→ENC sync toggle (X5) first — it is the only axis where ffmpeg is strictly stronger and the cheapest toggle — but treat a cure as "sync OR timing" until the throttle control (X3) separates them. If X5 earns it, the minimal upstream fix is a consumer-side `frame->waitsync()` at the top of `PipelineTaskMFXEncode::sendFrame` (or `requireSync()` returning true for MFXVPP→MFXENCODE), validated by 60 clean iterations + whole-file md5 + single-session bit-exactness.

Second-best match is always ≤ 29.7 dB (typically 16–18 dB). The harness PSNR value is a fingerprint of the stale frame (12.82→289, 12.91→294, 13.22→291, 22.29→290 for 1129). Stale distance (299 − idx) = 10 / 8 / 5 frames (923), 9 frames (1129); all stale frames belong to the PRECEDING mini-GOP [289..294], whose coded order is 294, 291, 290, 289, 293, 292 — i.e. they are the frames whose encode tasks complete first, so their input surfaces are the first to be released. Phase 2's "0/17 cross-session swaps" is fully explained. (Counter-check of "cross-session": a visual check of it04 shows a coherent close-up of a man while the reference shows a woman in a corridor — a different shot of the SAME chunk.)

### F2 — Corruption is confined to the final truncated mini-GOP before the forced IDR

`[VERIFIED: ffmpeg whole-chunk psnr scan of ALL 30 corrupt outputs vs the isolated reference (13 from 8.31 + 17 from 8.22) — every one differs in exactly frames {295,296,297,298,299}; trace_headers BSF structure check on 923 it04 and the reference]`
- Only frames 295–299 differ from the isolated reference (30/30 outputs): 295–298 at 52–56 dB (drift from the corrupt anchor; values from the 6 outputs scanned in detail: 923 it04/it10/it20, 1129 it03/it13/it20), 299 at 15.74 dB (923, YUV PSNR; harness RGB value 12.82) / 24.99 dB (1129).
- Frame headers (565 coded frames) are identical to the clean reference except `base_q_idx` of the final mini-GOP (it04: anchor 77→73, B frames 100→81/83/85, 94→79): the encoder reacted to wrong anchor content; coded order/refresh flags/IDs are unchanged.
- Coding structure around the boundary (reference chunk923, coded order): **299** (hidden ARF, order_hint 43, refresh 241) → 297 (hidden) → 296 (hidden) → 295 (shown) → show_existing 296, 297 → 298 (shown) → show_existing 299 → **KEY at display 300**. KEY frames exist only at display 0 and 300. The corrupt frame is exactly the first-coded (anchor) frame of that group; because its input was stale, its recon is the stale picture (47–57 dB match to an independent encode of the same source frame, NOT a bit-copy, ⇒ the encoder consumed a stale INPUT surface; a stale reference/recon would produce drift garbage, not a clean copy).
- The ffmpeg `av1_qsv` control encode has the **identical** coded sequence at display 283–300 (same order_hints, refresh flags, IDR at 300). The structure is not what differs.

### F3 — Whole-file md5 vs the isolated reference is a perfect, GPU-free corruption detector

`[VERIFIED: md5sum over 120 saved outputs]` A clean concurrent run is bit-identical to its scene's isolated reference. 8.31: 13 of 60 outputs differ, Phase-1: 17 of 60; every differing output is a hot scene (923/1129) that the harness had already flagged `corrupt=1`, and every flagged one differs — no corruption elsewhere, 928 is bit-identical in 40/40. The isolated reference md5s are **identical across qsvencc 8.22 and 8.31** (923 `ca77cc72b0cfa2cfd291f278ab62f278`, 928 `0c37720dd1886fceef86b45abe24d389`, 1129 `e0061679b2904499162081e5b0ef96ef`), so these md5s are the single-session bit-exactness target for any patched build. The harness only inspects frame 299/96; md5 additionally catches a corruption at ANY frame and any near-identical stale frame the 30 dB threshold would miss.

### F4 — The hotspot is the AV1 GOP end, not a source scene cut

`[VERIFIED: ffprobe of the source, read-only]` Source structure at the hotspots: scene 923 idx 299 = H.264 `I` (`key_frame=1`; keyframes at 263, 270, 278, 299); scene 928 idx 96 = `I` (periodic, 48/72/96); scene 1129 idx 299 = `B` (keyframes 264, 288 only — no keyframe/cut at 299). So a source cut/IDR is not required; the common property of 923 and 1129 is "chunk idx 299 = last frame before the AV1 IDR at 300". Scene 928 (111 frames) never reaches a GOP end inside the chunk (its end-of-stream flush path is clean 40/40), which is why its documented offset 96 never reproduces. Reporter text of rigaya/QSVEnc #308 ("frame of the previous scene") is consistent with a stale own-session input surface.

### Runtime facts that bound the hypotheses (vpl-gpu-rt `intel-onevpl-26.2.2`) `[CITED]`

- Encoder input lock lifetime: `core.IncreaseReference(*tpar.pSurfIn);` at `EncodeFrameAsync` time (`av1ehw_base_general.cpp:1366-1368`); `SetIf(task.pSurfIn, task.pSurfIn && !core.DecreaseReference(*task.pSurfIn), nullptr);` in `FreeTask` (`:1734`), which `TaskQueryInner` calls after the query loop for every task, hidden ARFs included (`ehw_task_manager.cpp:291-296`). So `Locked` on the encoder input spans submit→GPU completion.
- No input copy for our config: the internal Raw pool exists only `if (par.IOPattern == MFX_IOPATTERN_IN_SYSTEM_MEMORY)` (`:1032`); for video memory the GPU reads the app surface directly via `core.GetExternalFrameHDL(*task.pSurfReal, task.HDLRaw)` (`:1529-1530`) at submit time.
- Scheduler dependencies are by POINTER: ENC call registers `task.pSrc[0] = surface; task.pSrc[1] = bs; … task.pDst[0] = … bs` (`libmfxsw_encode.cpp:768-771`); VPP registers `task.pSrc[0] = in; task.pDst[0] = out;` (`libmfxsw_vpp.cpp:365-366`, two-entry-point variant `:388-389,406-407`); a new task "will sync on the first matching entry" of the table (`mfx_scheduler_core.cpp:431-432,440-484`). AV1 encode tasks are serialised: `GetThreadingPolicy()` returns `MFX_TASK_THREADING_INTRA` (`av1ehw_base_impl.h:104-106`; `MFX_TASK_THREADING_INTRA = MFX_TASK_INTRA`, `mfx_task_threading_policy.h`), chained in `AddTask` (`mfx_scheduler_core_ischeduler.cpp:562-576`). `MFXVideoCORE_SyncOperation` is just `session->m_pScheduler->Synchronize(syncp, wait)` (`libmfxsw_async.cpp`) — the same completion ffmpeg waits on and the scheduler dependency waits on. ⇒ "ENC submitted before VPP completed" is not predicted by the scheduler logic; a cure by explicit sync would therefore be a timing/serialisation effect or a path where the dependency is not honoured — to be MEASURED.
- GOP end: frame type for `(fo + 1) % gopPicSize == 0` is already `P|REF` at pre-reorder (`av1ehw_base_general_defaults.cpp:704-712`), so the anchor 299 is selectable as soon as its own task exists; when an IDR task is in the list `bFlush |= (stopIt != end)` (`av1ehw_base_task.cpp:109-111`) and `Reorder` may force the last frame to P-ref (`av1ehw_base_general.cpp:2914-2919`). `GetMaxParallelSubmits()` = `AsyncDepth==1 ? 1 : min(2, …)` and reorder is skipped while `stages(S_REORDER)+m_nTasksInExecution >= m_maxParallelSubmits` (`av1ehw_base_task.cpp:41-49`, `ehw_task_manager.cpp:145-147`) ⇒ the anchor's GPU submission can be deferred to a later call's async routine.
- H.264 decoder surface accounting: `numMin = dpbSize + 2 * asyncDepth` with the comment "2nd AsyncDepth ensures app can sync non-reference frames to free surfaces when all AsyncDepth pending syncpoints are reference frames" (`mfx_h264_dec_decode.cpp:977-980`) — the library's usage contract presumes the application syncs decoder outputs; qsvencc never does (a reason to keep X6 on the ladder).
- Linux media-driver 26.2.2: `Mos_Specific_SyncOnResource` and `Mos_Specific_SyncGpuContext` are empty stubs (`mos_os_specific.c:5195-5206` and following), `SkipResourceSync` is applied only to internal status/BRC/heap buffers (not app surfaces) ⇒ VPP-write→ENC-read ordering on a surface relies on kernel implicit fencing `[CITED: media-driver@intel-media-26.2.2; SkipResourceSync users via sourcegraph search]`. iHD binary exposes user-feature knobs read from `/etc/igfx_user_feature.txt`: `EnableSyncSubmission{Decode,Encode,VPP}` (+`SyncSubmissionTimeOut*`, header comment "IP alignment support"), `Enable HW Semaphore`, `Disable MMC`, `Native Fence Mode` (`mos_util_user_feature_keys.h:479-484`); their semantics are UNVERIFIED (see Assumptions).

## Instrumentation design (D-02/D-03)

**Mechanism:** new QSV-specific header `QSVPipeline/qsv_surf_trace.h` (draft tested standalone in `scratch/trace-sketch/`, record = 56 bytes, lock-free `fetch_add` ring, `QSVENC_TRACE_FILE` enables, `QSVENC_TRACE_CAP` log2 size default 18 ⇒ 14.7 MB, flush once at process exit with `fopen("wbx")` so an existing trace is never clobbered, decoder `qsv_trace_dump.py`). Compile-time `#define QSV_SURF_TRACE 1` inside the header (no meson flag change ⇒ only the 4 TUs that include `qsv_pipeline_ctrl.h` rebuild). Trace commit stays separate from the fix (D-11). Per-event cost ≈ 0.2 µs ≪ frame time (≈4.4 ms/frame at 226 fps) so masking is unlikely, but D-03's gate still applies.

## Build & deploy mechanics (C)

- **Rebuild:** `ninja -C /workspaces/qsvenc-831/build` (meson already configured). Editing `qsv_pipeline_ctrl.h` rebuilds exactly 4 objects (`QSVEncC.cpp.o`, `qsv_pipeline.cpp.o`, `rgy_filter_ssim.cpp.o`, `rgy_parallel_enc.cpp.o` — from `ninja -t deps`). Measured: compiling `qsv_pipeline.cpp` alone = 31 s (bottleneck), link = 2.2 s ⇒ incremental ≈ 35–40 s. The link is deterministic (re-link of unchanged objects reproduced `build/qsvencc` byte-for-byte). The binary has no RUNPATH and no unresolved libs (`readelf -d`, `ldd`) ⇒ it can be copied anywhere.
- **DANGER:** `scratch/repro-831/bin/qsvencc` is a SYMLINK to `build/qsvencc`; any `ninja` run silently changes what the "stock" harness copy executes. First task: `mkdir -p scratch/bins/stock-8.31 && cp -p build/qsvencc scratch/bins/stock-8.31/ && sha256sum` (current sha256 `f4282c494a1fe0565e568b7c35285d416a64b36265ffa93d5ffa362ec3c3cbdb`), then stop using the symlink.
- **How the harness finds the binary:** bare `qsvencc` on `PATH` (and bare `ffmpeg`); `W` = directory of the running `harness.sh` (`lib.sh`: `W="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"`), so a copied harness writes `runs/`, `control_runs/`, `report.csv`, `summary.txt` into its own directory. Without a prepended PATH it silently runs `/usr/bin/qsvencc` (8.22) — always assert the version line in the logs (`QSVEncC (x64) 8.31 (r4604) … <build date>` appears in each `runs/itNN/log923.txt`).
- **Per-candidate isolation without touching the harness:** `scratch/cand-tools/cand_setup.sh <name> <binary>` (tested with a fake binary): refuses to reuse a dir, copies `harness.sh`/`lib.sh` from the tracked `scratch/repro/` and aborts if their sha256 differ from the pins, symlinks the shared stock references, copies the binary to `bin/qsvencc.real` (+ sha256) and writes a `bin/qsvencc` PATH shim that exports `bin/cand.env`, drops args in `bin/cand.strip` (with their value), appends `bin/cand.add`, and (if `QSVENC_TRACE_ENABLE=1`) sets `QSVENC_TRACE_FILE` from `-o`. Run: `cd scratch/cand-<id> && PATH="$PWD/bin:$PATH" ./harness.sh run-batch 20 2>&1 | tee batch.log`.
- **Sequential screening instead of full batches:** `scratch/cand-tools/cand_screen.sh <cand-dir> [MAX=20]` calls the harness's own `run-iter`, stops at the FIRST corrupt hot frame (D-08: not a fix) — a non-fix is rejected in ≈1.8 iterations on average (P(any hot corrupt)=0.545), 98 % within 5 — and prints `ESCALATE-TO-60` after 20 valid clean iterations. Logic tested with stubs only; GPU behaviour UNTESTED. Official artifacts (D-03 gate, 60-run validation) use `run-batch` (summary.txt with Wilson CI).
- **Single-session bit-exactness + fps gate:** `scratch/cand-tools/cand_bitexact.sh <binary> <outdir>` (syntax-checked only, needs the exclusive GPU) encodes each scene twice sequentially with the harness's exact COMMON/seek/trim and compares md5 with the stock references above; prints fps (stock 3-way fps from the 8.31 logs: 923 226.6 [224.3–230.3], 928 131.2, 1129 230.1).
- **Timing:** 8.31 batch of 20 iterations ran ≈ 8.5 min (first run dir 07:32:33 → last 07:41:04) ≈ 26 s/iteration (3 qsvencc ≈ 1.5 s + PSNR extraction + 3-way ffmpeg control + PSNR); 60 iterations ≈ 26 min; ≈ 1 GB per 20 iterations on a 234 GB free volume.
- **No-rebuild levers via the shim:** X2 (`cand.strip`: `--tune`, `--scenario-info`), X3 (`cand.add`: `--max-procfps 60`), X8 (`cand.env`: `LIBVA_TRACE=<prefix>`; libva writes `<prefix>.<pid>.thd-<tid>`), `--task-perf-monitor` (per-task stopwatch incl. `getWorkSurf` wait time ⇒ pool-pressure estimate, printed at the end of `RunEncode2`, qsv_pipeline.cpp:6185-6207), `--log-level debug` (pool sizes/types).

## D-01 offline method (D) — tools tested this session (no GPU, `/data` read-only)

- `scratch/d01-tools/d01_md5.sh <workdir>`: S/D matrix of every `runs/itNN/cSSS.obu` vs its isolated reference; 1.2 s.
- `scratch/d01-tools/d01_scan_ref.sh <ref.obu> <corrupt.png> <nframes> <log>`: PSNR of one PNG against all reference frames (`-loop 1` still image, `format=rgb48be` on both sides, `psnr=stats_file`); stats `n:` is **1-based** (`n:300` = index 299); ≈ 6–20 s per corrupt frame.
- `scratch/d01-tools/d01_scan_batch.sh <workdir> <outdir>`: runs it for every `corrupt==1` row of `report.csv` and prints `STALE_OWN_FRAME(<idx>)` (best ≥ 35 dB and idx ≠ hotspot) — all 13 rows of the 8.31 batch classify `STALE_OWN_FRAME` (4 min total).
- `scratch/d01-tools/d01_fullscan.sh <workdir> <outdir>`: lists every frame index that differs from the reference for each D output (all 30 historic corrupt outputs: exactly 295–299; ≈1.3 min for the 13 of 8.31, ≈3 min for the 17 of 8.22).
- `scratch/d01-tools/d01_struct.py` + `ffmpeg -i X.obu -c copy -bsf:v trace_headers -f null - 2>trace.txt`: coded-frame order/hidden/shown/show_existing, KEY positions.
- Source comparison: `ffmpeg -ss <seek> -i SRC -i corrupt.png(-loop 1) … psnr` (6 s). **Pairing pitfall:** do NOT pair the source (24 fps) with an OBU stream (default 25 fps) frame-for-frame — `psnr` pairs by timestamp and drifts; the looped-still approach is immune; for 1:1 alignment add `setpts=N/24/TB` to both inputs.
- Result discriminators: stale own frame = one exact earlier frame ≥ 40 dB with every other frame ≤ 30 dB (observed); mixed/partial = two frames ≥ 25 dB or a smeared best match; garbage = all < 20 dB; cross-session swap = ≥ 35 dB against another scene (0/17 in Phase 2); reference drift (not a swap) = neighbours 52–56 dB.

## Common Pitfalls

1. **Silent wrong binary.** Harness resolves `qsvencc` from `PATH`; unprefixed PATH runs `/usr/bin/qsvencc` (8.22). Assert the version/build-date line in `runs/it01/log923.txt` and the candidate's `qsvencc.real.sha256` after every batch.
2. **Mutable stock binary.** `repro-831/bin/qsvencc` → `build/qsvencc` changes on every rebuild. Archive first.
3. **Instrumentation masks the race.** Run the D-03 gate with tracing ENABLED (trace only; polls in a separate gate); if the rate collapses, record it as timing evidence (D-03) and use no-rebuild levers.
4. **PSNR classifier blind spots.** The harness checks only frame 299/96 and `<30 dB`; a stale frame from the same shot could score >30 dB. Always add `d01_md5.sh` for any candidate claim. For parameter-variant runs (X2/X3/X9) md5-vs-stock-reference no longer applies — use variant references or PSNR.
5. **Trace lost on kill.** The harness kills encodes after `ENCODE_TIMEOUT` (120 s, env-overridable) with SIGTERM; the trace flushes only on normal exit — fine at ≈1.5 s/run, but never debug a hang with the ring.
6. **Never reuse a candidate dir.** `wbx` trace files and `runs/itNN` would be stale; `cand_setup.sh` refuses.
7. **Sequential GPU.** Use the harness's `gpu_clients`/`cleanup_gpu_procs` (sourced from `lib.sh`) before any manual encode; no parallel experiments on the A380. A `--log-level debug` single-session run for pool sizes also needs an idle GPU.
8. **`waitsync` return codes are ignored** in `PipelineTask::getOutput` (`:604`) and `waitsync` clears the syncpoint even on `MFX_WRN_IN_EXECUTION` (`:353`); `MSDK_WAIT_INTERVAL` is large (`:67`), but a sync-based fix should not rely on the return value.
9. **`requireSync` lambda has a latent unsigned-loop bug** (`for (size_t prevtask = srctask-1; prevtask >= 0; …)`, qsv_pipeline.cpp:5991) — do not touch it in the fix.
10. **Frame-count alignment:** qsvencc `--trim 0:339` is inclusive (340 frames) while the harness control encodes `-frames:v 339`; control references are separate (`control_reference/`) — never compare qsvencc and control frames 1:1 across the two.
11. **Rebuild changes timestamps in worktree branches:** switching `diag/*` ↔ `fix/*` in the same `build/` dir forces rebuilds; always rebuild, re-archive, re-hash before a batch.
12. **Do not re-test already-inert levers** (`rt_format`, `VASurfaceAttribUsageHint`, the CLI `--async-depth 1`, `--disable-va`) — out of scope per CONTEXT. Note the CLI flag only changes pool size and VPP AsyncDepth (F5), so it is not evidence about the encoder's own AsyncDepth.
